I’d structure this as a **standalone healthcare interoperability product**, not as an extension of MyLikita. The PRD below is written so it can serve as a foundation for engineering, product planning, partner discussions, and eventually commercial documentation.

# Product Requirements Document (PRD)

## Healthcare Device Integration & Interoperability Platform

**Working Product Name:** Integration Hub
**Product Category:** Healthcare Interoperability / Medical Device Integration
**Document Version:** 1.0
**Status:** Product Definition
**Target Market:** Hospitals, diagnostic laboratories, radiology centers, LIS/HIS/EHR vendors, medical equipment distributors, healthcare technology companies

---

# 1. Executive Summary

The **Integration Hub** is a vendor-neutral healthcare interoperability platform designed to connect medical devices and healthcare information systems through standardized protocols and configurable adapters.

The platform acts as an intermediary between:

* Laboratory analyzers
* Imaging modalities
* Medical devices
* LIS
* HIS/HMS
* EHR
* RIS
* PACS
* Other healthcare applications

The fundamental problem it solves is that healthcare facilities operate equipment and software from multiple vendors, each potentially using different communication protocols, data formats, network configurations, and proprietary implementations.

Instead of every LIS/EHR vendor building a custom integration for every device, Integration Hub provides a centralized interoperability layer.

### Concept

# 2. Product Vision

### Vision Statement

> **Create a universal interoperability layer that allows healthcare software and medical devices from different vendors to communicate without requiring custom point-to-point integrations.**

The long-term objective is to make connecting a new medical device similar to configuring a network printer or payment gateway rather than developing a new software integration from scratch.

---

# 3. Problem Statement

Healthcare facilities frequently operate heterogeneous technology environments.

For example:

```text
Hospital
│
├── MyLikita HMS
├── LIS
├── PACS
├── Roche Analyzer
├── Mindray Analyzer
├── Sysmex Analyzer
├── X-Ray
├── CT Scanner
└── ECG Machine
```

Each device may have:

* Different protocols
* Different data formats
* Different communication methods
* Different patient identifiers
* Different test codes
* Different vendor implementations
* Different connection requirements

This creates several problems.

### 3.1 Point-to-point integration

Without middleware:

```text
LIS ───── Roche
LIS ───── Mindray
LIS ───── Sysmex
LIS ───── Abbott
LIS ───── Analyzer X
```

Every integration becomes a separate engineering project.

With Integration Hub:

```text
             ┌─────────────┐
             │     LIS     │
             └──────┬──────┘
                    │
                    ▼
             ┌─────────────┐
             │ Integration │
             │     Hub     │
             └──────┬──────┘
                    │
       ┌────────────┼─────────────┐
       ▼            ▼             ▼
    Roche        Mindray       Sysmex
```

# 4. Product Goals

## Primary Goals

1. Provide vendor-neutral medical device connectivity.
2. Support standardized healthcare interoperability protocols.
3. Support both laboratory and imaging workflows.
4. Provide configurable device adapters.
5. Provide bidirectional communication.
6. Operate reliably in offline/local-network environments.
7. Provide centralized monitoring and diagnostics.
8. Reduce the engineering effort required for device integrations.
9. Provide APIs for LIS/HIS/EHR/RIS/PACS systems.
10. Maintain complete auditability of device communication.
11. Support multiple healthcare facilities.
12. Allow third-party healthcare software vendors to integrate with the platform.

---

# 5. Non-Goals

The initial product should **not** attempt to:

* Build an LIS.
* Build an EHR.
* Build a PACS.
* Replace existing hospital software.
* Manufacture medical devices.
* Control medical devices outside officially supported interfaces.
* Automatically interpret diagnostic results clinically.
* Provide medical diagnosis.
* Support every medical device from day one.

The platform is an **interoperability layer**, not a clinical application.

# 16. Internal Canonical Data Model

This is one of the **most important architectural decisions**.

The system should have an internal normalized model.

For example:

```json
{
  "patient": {
    "id": "P12345",
    "name": "John Doe",
    "dateOfBirth": "1990-01-01",
    "gender": "M"
  },
  "order": {
    "id": "ORD123",
    "accessionNumber": "ACC123",
    "tests": []
  },
  "device": {
    "id": "DEV001"
  },
  "results": []
}
```

Protocols then become translators.

```text
ASTM
  ↓
Canonical Model
  ↓
HL7

DICOM
  ↓
Canonical Model
  ↓
FHIR
```

This prevents protocol-specific logic from contaminating the core system.

# 21. Message Queue

Every message should pass through a durable queue where appropriate.

```text
Incoming Message
       ↓
Queue
       ↓
Validation
       ↓
Transformation
       ↓
Routing
       ↓
Destination
```

If destination fails:

```text
Retry
 ↓
Retry
 ↓
Retry
 ↓
Dead Letter Queue
```

---

# 22. Retry Mechanism

Configurable retry policy:

```text
Attempt 1 → immediate
Attempt 2 → 5 seconds
Attempt 3 → 30 seconds
Attempt 4 → 5 minutes
Attempt 5 → 30 minutes
```

Failed messages should never silently disappear.

---

# 23. Dead Letter Queue

Messages that cannot be processed should enter a DLQ.

Administrators can:

```text
View
Inspect
Correct
Replay
Discard
```

This is particularly important for laboratory results.

# 39. Configuration-Based Adapters

Rather than writing code for every device, support configuration where possible.

Example:

```yaml

  manufacturer: Mindray
  model: BS-430
  protocol: ASTM
  transport: tcp

connection:
  host: 192.168.1.20
  port: 5000

mapping:
  GLU: glucose
  CREA: creatinine
```

However, the architecture must allow custom code adapters for devices with non-standard behavior.

# 40. Generic Adapter Interface

Conceptually:

```typescript
interface DeviceAdapter {
  connect(): Promise<void>;

  disconnect(): Promise<void>;

  sendOrder(order: CanonicalOrder): Promise<void>;

  receiveMessage(): Promise<RawMessage>;

  parse(message: RawMessage): Promise<CanonicalMessage>;

  healthCheck(): Promise<DeviceStatus>;
}
```

Then:

```text
ASTMAdapter
HL7Adapter
DICOMAdapter
VendorSpecificAdapter
```

all implement the appropriate interfaces.

# 66. Key Risks

## Risk 1 — "Universal" becomes unrealistic

There will always be devices with proprietary implementations.

Mitigation:

> Generic protocols + adapter architecture + certified integrations.

---

## Risk 2 — Device-specific quirks

Two ASTM devices may behave differently.

Mitigation:

> Device profiles and configurable adapters.

---

## Risk 3 — Patient/result misassociation

Potentially serious clinical consequences.

Mitigation:

* Multiple identifiers
* Validation
* Exception queues
* Audit trails
* No silent fallback matching

---

## Risk 4 — Network instability

Mitigation:

* Edge gateway
* Durable queues
* Offline mode
* Retry

---

## Risk 5 — Scope explosion

Trying to support:

```text
Lab
X-Ray
CT
MRI
ECG
Ventilator
...
```

from V1 would likely slow the project dramatically.

Mitigation:

> Laboratory first → imaging second → broader medical devices later.

# 67. Critical Product Principle

There is one principle I would put at the top of the engineering documentation:

> **The Integration Core must never depend directly on a specific device vendor or protocol.**

Instead:

```text
                Canonical Model
                     ▲
                     │
             Transformation
                     ▲
                     │
               Protocol Layer
                     ▲
                     │
                Device Adapter
                     ▲
                     │
                   Device
```

That architectural separation is what allows the system to scale from:

**one analyzer**

to

**hundreds of device models.**

# 68. What I Would Do With Your Existing Middleware

I would **not rewrite it immediately**.

First, treat the existing repository as a **reference implementation / V0 adapter**.

Perform an architectural extraction:

```text
Existing Middleware
       │
       ├── ASTM parser
       ├── Device communication
       ├── Order handling
       ├── Result handling
       └── Existing mappings
```

Then extract reusable components:

```text
                 New Platform
                      │
             ┌────────┴─────────┐
             │                  │
       Integration Core    Device Adapters
             │                  │
             │           Existing analyzer
             │              integration
             │
             └── Canonical Model
```

This lets you preserve the working knowledge you already gained while avoiding the mistake of making the new platform dependent on the architecture of the old project.

# 70. Final Product Positioning

The strongest way I would describe the product commercially is:

> **A vendor-neutral healthcare interoperability platform that connects laboratory analyzers, imaging equipment and other medical devices to LIS, HIS, EHR, RIS and PACS systems through standardized protocols and configurable integrations.**

And the simpler sales message:

> **Connect any medical device to any healthcare system.**

That is a much stronger long-term product proposition than **"analyzer middleware."**

Most importantly, **you already have the hardest starting asset: practical experience making an analyzer communicate with an information system.** The next step isn't to throw that away and build a giant universal platform. It's to extract the protocol/device communication layer you already proved, put a proper canonical model, routing, queueing, mapping and management layer around it, and then progressively add DICOM and other device domains.
